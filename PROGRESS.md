# Progress

Task state only. [PLAN.md](./PLAN.md) holds the design and the reasoning — when the two
disagree, PLAN.md wins and this file is stale.
[IMPLEMENTATION.md](./IMPLEMENTATION.md) records what the code actually is, every
deliberate deviation, and what turned up when the design met real data.

**Where things stand: M0–M6 have a working MVP end to end.** Constraint language,
store layout, both write paths, SQL query, views, a STAC API, and all four examples.
55 Rust tests and 53 Python tests pass (`make test`).

**What wants your attention first**, in order:

1. **Three MVP scope reductions to accept or reject** — the Rust crates do no IO
   (the storage driver is Python), `zarr-collection-query` does not exist as a crate,
   and the STAC API is plain FastAPI rather than stac-fastapi. All three are argued in
   IMPLEMENTATION.md; none reopens a closed decision, but all three are yours to
   confirm.
2. **The extra-columns gap was filled provisionally**, because nothing could be built
   without it: declared at `create_collection`, supplied per member at `add_item`.
   It is the minimum that works, not a decision — see below.
3. **The MAST-U finding**, which is the most interesting thing the implementation
   learned: the referenced unit had to go one level finer than the plan predicted.

Not to be decided as a side effect of implementation work. Neither was touched.

- [ ] **Serialisation substrate** — **v1 assumes Icechunk-Zarr, so nothing is blocked.**
      Worth revisiting deliberately at some point, since reopening it reaches layout
      decisions 1, 5 and 6 and gets more expensive the later it happens.
- [ ] **Nullability** — narrowed: schema evolution no longer needs it, so only
      genuinely-missing *source* values remain. Nothing in the MVP needed a null.

## Unresolved design gaps

- [ ] **How extra column values get supplied — answered provisionally, wants your
      ruling.** The MVP takes `create_collection(extra_columns=[ExtraColumn("shot",
      "int64")])` plus `add_item(ds, extras={"shot": 30420})`. Chosen because extra
      columns are by definition not recomputable from a member's group, so nothing
      else *could* supply them. What it does **not** do is *derive* an extra column
      from the member — a `bbox` computed from the attributes, say — which is the
      obvious next ask and would want a declared derivation. Left open on purpose.

- [x] `substitute` inverts `meet` exactly

- [ ] **Not done:** the property tests run over *generated* documents plus the five
      domain fixtures, not "a few hundred real OME-Zarr and Sentinel-2 `zarr.json`
      documents from public stores". Worth doing; it is the test most likely to catch
      an encoding assumption.

Answered while building:

- [x] **Does the substrate write consolidated metadata?** Icechunk does not support
      consolidated metadata *at all* — `zarr.consolidate_metadata` raises on an
      `IcechunkStore`. The description is therefore derived by walking the group's
      children. One-document-per-group survives intact.
- [ ] **Do attribute key sets vary in practice?** Still open. The four examples were
      each scoped to a uniform unit, so none forced the question — which is itself
      mild evidence that the finer-unit technique keeps working.

Findings, all in `examples/README.md` and IMPLEMENTATION.md:

- [x] **MAST-U structure confirmed** — Zarr **v2**, per-diagnostic subgroups
      (`/amc/plasma_current`). A shot is not a flat unit, as suspected.
- [x] **And one step further: signal availability varies *within* a diagnostic**, so
      (shot, diagnostic) would still have hit optionality. The example takes
      **(shot, diagnostic, signal)** — the plan's own technique, one level deeper.
- [x] **VirtualiZarr 2.5.1 has no TIFF/COG parser**, so Sentinel-2 cannot be
      virtualized yet. Members are written metadata-only; the virtual path is wired
      and used the moment a parser exists.
